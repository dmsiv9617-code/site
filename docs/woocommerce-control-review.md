Дата: **5 ноября 2026, Europe/Moscow**. Цель: проверить и сохранить локальный прототип; не публиковать ветку, не создавать PR, не трогать main/Vercel/production.

## Вывод

Ветка **готова к публикации в GitHub как проверяемый локальный прототип после отдельного подтверждения пользователя**. Она **не готова к production и коммерческим платежам/доставке**. Подготовлен один локальный коммит со всей интеграцией, исправлениями и этим отчётом; SHA коммита выводится отдельно при завершении. Push/PR/merge/deploy не выполнялись.

После исправлений пройден полный путь от получения одного Woo-товара и выбора параметров до гостевого classic checkout, HPOS-заказа **№21**, просмотра снимка мастером и скачивания приватного PNG. Тестовый BACS не переводит деньги и не вызывает Ozon. Проверка чистой установки на дополнительных одноразовых volumes **заблокирована местом Docker**, а не считается успешной.

## Архитектура: ответы

**1. Домены и адреса.** Сейчас это локальные **разные origins на одном hostname**: Vite `http://localhost:5173`, WordPress/checkout `http://localhost:8088`. Это не production единый origin и не поддомены. Vite проксирует `/wp-json` на backend, classic checkout открывается на 8088. Cookie не привязаны к порту, поэтому localhost-сессия общая. Нельзя автоматически переносить этот результат на `127.0.0.1`, разные домены или Vercel preview. Для production предложен один HTTPS-origin с reverse proxy к `/wp-json`, `/checkout`, `/cart`, `/my-account`, `/wp-admin`; конфигурация не применялась.

**2. Сессия корзины.** Стандартная гостевая WC cookie-сессия и Store API `Cart-Token` в заголовке, `credentials: include`. Первоначальные `/session` и GET cart устанавливают/восстанавливают WC сессию; токен хранится в памяти адаптера. После reload новый GET восстанавливает корзину по cookie. Для upload используется отдельный случайный nonce, сохранённый в той же WC сессии. Сам Cart-Token — bearer credential; его кража не исключается этим прототипом, его нельзя логировать или экспортировать. В клиенте нет секретных WC REST API-ключей.

**3. Физическое хранение.** Клиентские макеты — named volume **`woodbase-local_private`**, внутри WP-контейнера **`/var/woodbase-private`**, на Docker daemon host: **`/var/lib/docker/volumes/woodbase-local_private/_data`** (проверено volume inspect). Это вне Nginx webroot `/var/www/html`. WordPress media содержит только публичное изображение каталога, не клиентские рисунки. Метаданные владельца — серверные WP options; fileId/параметры — в WC cart/order snapshot через CRUD, совместимо с HPOS.

**4. Защита файлов.** Upload: allowlist Origin, session nonce, uploaded-file check, лимит 5 MiB, MIME по содержимому/finfo/getimagesize, PNG/JPEG/WebP, max 4096 px и 16M pixels, декодирование/пересохранение PNG, случайный 128-bit ID, HMAC-владелец сессии, 10 атомарно резервируемых попыток на сессию. Private directory 0700, PNG 0600. При добавлении fileId проверяются владелец и наличие файла. Выдача: только администратор/менеджер с `manage_woocommerce`, item-bound WP nonce, проверка order item и существующего заказа, whitelist ID, attachment/nosniff/no-cache headers. Публичного endpoint выдачи клиентского PNG нет.

**5. Удаление временных файлов.** Сырой multipart temp-файл удаляется PHP после запроса. Для уже сохранённых приватных PNG **автоматическая очистка не реализована**: также сохраняются файлы без заказа, receipts и quota options. При удалении позиции файл не удаляется. Это сохраняет производственные снимки, но не заменяет production retention. Нужны согласованные сроки, поиск ссылок из активных корзин/заказов, dry-run, блокировки от гонок, backup и безопасная очистка orphan-файлов. Рабочие private/db volumes не удалялись. Disposable-проект `woodbase-review-fresh` удаляет только собственные новые ресурсы после отказа переиспользовать существующие.

**6. Production-ограничения.** Не выбраны/не настроены HTTPS origin/proxy/cookie/cache; WP URLs и bootstrap локальные; нет общей защиты upload по IP/пользователю, мониторинга, backup/retention/очистки служебных options; товарные данные и надбавки не утверждены, test SKU virtual без доставки; схемы опций редактируются в коде, не отдельным admin UI. Версии WP 6.8.3/WC 10.3.5/PHP 8.3.28 проверены только как фиксированный тестовый набор; нужна проверка актуальной поддержки/обновлений, без утверждений о конкретных неустановленных CVE. Оплата/доставка Ozon и производственный checkout не допущены. Из старого JSON нельзя восстановить полный исходник рисунка — после импорта нужно заново загрузить оригинал.

**7. Classic без Blocks.** Да. Рабочая страница содержит `[woocommerce_checkout]`, и полный гостевой заказ выполнен через её стандартную форму. Blocks checkout UI для этого пути не нужен. Наличие внутренних Blocks/Store API библиотек в пакете Woo не означает обязательность визуального Checkout Blocks. Предыдущая отдельная страница Blocks показывала пустую корзину при работающем API checkout; она не является допущенным путём. После этого контроля Blocks UI не сертифицируется.

**8. Редактирование checkout.** Сейчас небольшая палитра/скругления добавлены через условный `wp_head` собственного плагина; форма остаётся WooCommerce. Контент страницы вокруг shortcode можно менять в WordPress. Для поддерживаемого дизайна следующего релиза CSS следует вынести в отдельный versioned файл и enqueue, раскладку/поля менять штатными Woo hooks; при необходимости шаблоны переопределять только в дочерней теме с контролем версий Woo templates. Gutenberg Block controls не управляют внутренностями classic shortcode. Не править Woo core, не создавать собственную платёжную форму; перед релизом повторить Ozon compatibility и guest tests после стилизации.

## Замечания по приоритету

**Критические для production, остаются открытыми:** не подтверждена совместимость и не проверены коммерческие payment/shipping модули; отсутствует проверенная production-схема origin/session/HTTPS и production-политика работы с клиентскими файлами. Это блокеры коммерческого запуска, а не утверждение, что проверенный локальный guest flow сломан. Исправленные критические дефекты перечислены выше.

**Важные:** автоматическая очистка orphan-файлов/receipts/quota options и общий rate limiting отсутствуют; fresh install повторно заблокирован MariaDB errno 28 `No space left on device`; остаётся повторить на достаточном диске. В Docker только используемые образы, агрессивная очистка не выполнялась. Test SKU virtual, финальная цена/комплектация/доставка не утверждены; схема опций фиксирована в плагине; Blocks UI не принят. До production требуется обновление/проверка поддерживаемых версий и backup/monitoring.

**Некритические для локального прототипа:** часть checkout/system labels — на английском из локальной WP установки; CSS checkout пока inline вместо отдельного файла/child theme. Предсуществующий standalone `export:html` не является проверенным каналом этой интеграции (старый exporter оставляет module imports в обычном script); поддерживаемый и проверенный канал — Vite. Полный аудит всех анимаций/браузеров/keyboard/screen readers не выполнялся.
