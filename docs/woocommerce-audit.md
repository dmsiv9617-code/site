# WoodBase: аудит и архитектура прототипа WooCommerce

Дата: 2026-11-05. База — актуальная `origin/main`, полученная через `git fetch origin main`: `3777405dbfa6c0f42978ddfc1c941060b843da40`. Ветка `feature/woocommerce-integration`. Main, Vercel, PR и коммерческие аккаунты не изменялись. Первоначальные ограничения proxy/Docker устранены штатным запуском команд вне ограниченного shell sandbox. Apache-образ не поместился в Docker-хранилище; применён компактный официальный FPM Alpine + Nginx без смены архитектуры приложения.

## Архитектура

- `index.html`: русский SEO, WB SVG/preloader, sessionStorage `wb-intro`, точка входа `/src/main.js`.
- `src/main.js` (858 строк): каталог, шаблон страницы, конструктор, загрузка рисунка, корзина, проект, маршрутизация по hash, анимации. Серверного каталога и оформления заказа нет.
- `package.json`: Vite ^6.4.1 (локально сборка 6.4.4), GSAP ^3.15.0; vanilla JS, без React. Сохранить обе зависимости и lockfile.
- `src/album-variants.js`, JSON: 96 комбинаций 6 моделей × 4 цвета × 2 цвета кожи × 2 переплёта. Числовые индексы используются сохранёнными проектами: не переупорядочивать.
- `src/album-preview.js`: асинхронное декодирование, защита от устаревших результатов, переходы, reduced-motion. Не заменять.
- `src/header-collection.js`, `favorites.js`: шапка/избранное, отдельный localStorage `woodbase-favorites-v1`.
- CSS: preview, studio, header-collection, benefits, workshop-teaser, concept, brand, intro и базовые стили. GSAP используется для intro/hero; остальные эффекты включают canvas, Web Animations, IntersectionObserver и обработчики прокрутки. Не переносить на шаблоны WP.
- `public/`: утверждённые изображения, варианты, кадры Вуди. Их не требуется переносить в WordPress для прототипа.

## Товарные данные — требуют подтверждения

Шесть моделей заданы в массиве `models` в main.js, тестовая «Счастливые моменты» имеет индекс 5. `albumBasePrice=3540`, `total()` всегда возвращает её, цены сохранённой корзины при загрузке перезаписываются этой величиной. Размер 33 × 22 см, корешок 3 см, тексты комплектации зашиты отдельно в интерфейсе. Нельзя считать их утверждёнными данными WooCommerce.

Цвета: natural/walnut/black/copper; переплёт bolts/woven; кожа black/brown. Дополнения corners/markers/stickers считаются включёнными. box и metric имеют неизвестную стоимость; live-заказ должен блокировать их до появления серверной цены, а не назначать ноль.

## Конструктор, рисунки и проекты

`state` хранит model/motif/color как индексы, binding/leather как строки, inscription, extras, image, placement, threshold/mode и page. `variantFor` показывает готовое фото только при совпадении заводской надписи/рисунка; иначе рендерится редактируемый эскиз. Положение, масштаб, поворот и порог применяются в браузере.

Загрузка принимает PNG/JPEG/WebP до 5 MiB, декодирует createImageBitmap, уменьшает до 600 px и сохраняет PNG data URL в state. Оригинал теряется. Это preview, НЕ производственный исходник. До live-режима необходимо сохранить исходный File отдельно, загрузить приватно на сервер, проверить реальный MIME/размер/разрешение/декодирование, исключить SVG и архивы. При замене/удалении рисунка сбрасывать fileId. Предсказуемый uploads URL и публичное WP-вложение для клиентского макета неприемлемы.

`woodbase-project`: сохранение проекта в браузере; `project()` экспортирует version=1/brand/configuration в JSON. Импорт до 5 MiB проверяет поля, диапазоны и PNG data URL; не использовать его как серверную валидацию. Сохранить старый формат, добавить отдельный версионированный AlbumConfiguration для API.

## Корзина и заказ

`sloy-cart` хранит массив с клиентской ценой, превью, названиями опций и копией state. Счётчик считает позиции. Есть удаление; изменения количества нет. Экспорт `album-order-draft.json`, копирование текста и открытие Telegram — только черновик запроса, никакого заказа на сервере. Telegram username пустой. Существующие черновики не мигрировать автоматически в live-корзину.

## Реализованная архитектура

- `src/commerce.js`: отдельный AlbumConfiguration v1 со стабильными IDs, placement, fileId и без клиентской цены; Store API Cart-Token/credentials/include, timeout и явные ошибки; update/remove.
- `src/commerce-ui.js`: demo по умолчанию, live включается явно. Только индекс 5 связан с одним Woo-товаром; backend отдаёт имя/описание/цену/картинки/наличие/разрешённые IDs. Прочие пять обложек остаются demo. Недоступность live блокирует добавление, а не подменяет серверную корзину локальным черновиком.
- `src/main.js`: сохранена композиция и preview; ограниченные hooks обновляют тестовый товар/цену в конструкторе и коллекции. Оригинальный File хранится отдельно от preview в памяти до отправки. Старые localStorage и JSON-проекты работают в demo.
- При восстановлении старого проекта с изображением live требует снова загрузить оригинал: эскиз 600 px не отправляется под видом исходника. После новой загрузки в заказ попадает PNG с исходным разрешением, без метаданных/встраиваемого содержимого. Это осознанное ограничение прототипа.
- `integrations/woocommerce/plugin/woodbase.php`: whitelist серверной конфигурации, цены только из WC, Store API extension, уникальные request receipts на сессию, приватные рисунки, перенос snapshot в WC_Order_Item_Product через CRUD, admin download с capability и nonce. Классическая форма товара не может обойти обязательную персонализацию. HPOS включён и проверен.
- Цена тестового SKU берётся из WooCommerce; включённые опции без надбавок. box/metric не допускаются в live, пока не задана стоимость. Схема опций в этой версии находится в собственном плагине, отдельного админ-редактора схемы нет.
- Приватные файлы вне webroot в volume `/var/woodbase-private`: случайный 128-bit ID, owner HMAC сессии, 0600, директория 0700. Проверяются MIME по содержимому, декодирование, 5 MiB, максимум 4096 px/16M pixels, PNG/JPEG/WebP; SVG не допускается. До 10 валидных попыток обработки на гостевую сессию, квота резервируется атомарно. Удаление/ротация служебных receipts и файлов пока ручные; production требует политики хранения, сирот и резервирования.
- Идемпотентность add-item: атомарный уникальный receipt с постоянным значением; повтор отвечает 409 и не увеличивает количество. Клиент не делает слепых повторов POST. Если ответ потерялся, открыть/обновить корзину; после неуспешной попытки с потреблённым ID нужен новый явный запрос. Это предотвращение дублей, а не возврат сохранённого первого ответа.

## Домен и checkout

Локально Vite `/wp-json` проксирует на localhost:8088, куки localhost общие для портов. Переход на backend checkout сохраняет ту же гостевую корзину; это проверено браузером. Cart-Token держится в памяти и не экспортируется; начальный GET восстанавливает cookie-сессию после reload. Секретных WC REST keys нет.

Для production предпочтителен один origin: frontend `/`, backend `/wp-json`, `/checkout`, `/cart`, `/my-account`, `/wp-admin` через явно настроенный reverse proxy, сохранение Set-Cookie/Location, исключение cart/checkout/session из кеша. Vercel rewrite не менялся. Требуется отдельно проверить WordPress URLs, cookie path/secure/samesite, TLS и headers. Произвольные frontend origins не разрешать: собственный плагин проверяет Origin до обработки REST; session nonce имеет no-store.

Поддомены требуют отдельного теста cookies/CORS/checkout. Preview на другом основном домене может упереться в third-party cookies. Cart-Token сам по себе не доказывает перенос cookie-сессии в checkout.

В локальной среде:

- Classic checkout: реальный гостевой тестовый заказ создан через штатную форму, вручную включённый локальный BACS «не оплачивать». Внешние шлюзы/доставка не подключены, email блокируется в WP_ENVIRONMENT_TYPE=local.
- Checkout Blocks: отдельная диагностическая страница показала пустую корзину, хотя guest checkout endpoint Store API успешно создал тестовый заказ. Эта проверка не доказывает работоспособность Blocks UI; альтернативная страница не назначалась основным checkout. Проблему нельзя считать исследованной до конца. Не применять Blocks для frontend handoff без отдельного исправления/проверки.
- Classic выбран только для локального прототипа по результату работающего браузерного пути. Окончательный тип для Ozon не выбран и совместимость не заявляется.

## Результаты и границы

Порядок запуска и команды проверки: `integrations/woocommerce/README.md`. Фактический отчёт: `docs/woocommerce-verification.md`. Два режима Vite собираются; существующие тесты и новые контракты проходят. Пройден реальный локальный путь от upload/UI до HPOS-заказа и скачивания PNG администратором. Реальные деньги/отправления не использовались.

Производственная эксплуатация не разрешается этим отчётом: требуются актуализация/проверка поддерживаемых версий WP/WC, production rate limits/хранилище/backup/retention, финальные товарные данные и физические габариты/масса, проверка схемы доменов, Ozon и выбранного checkout. Seed-товар специально virtual, чтобы изолировать проверку персонализации от доставки.

Существующий `scripts/export-html.mjs` оставляет ES-module imports в обычном script и не является проверенным способом standalone-экспорта этой версии; это обнаруженное ограничение исходной архитектуры, его исправление не включено в интеграцию. Vite остаётся основным проверенным способом запуска.
